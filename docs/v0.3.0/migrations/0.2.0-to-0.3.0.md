# Migrating from 0.2.0 to 0.3.0

The main code migration in 0.3.0 is that ECS components must be stored as
values, not top-level pointers. If your game already passes component values
and does not rely on the expanded default system set, no code changes are
required.

## Store components by value

`World.NewEntity`, `World.NewEntities`, `Entity.AddComponent`, and
`Entity.SetComponent` now reject a component whose top-level value is a
pointer. Replace pointer component construction with a value:

```go
// 0.2.0
entity, err := world.NewEntity(&Position{X: 10})

// 0.3.0
entity, err := world.NewEntity(Position{X: 10})
```

Apply the same change to `NewEntities`, `AddComponent`, and `SetComponent`.
Component reads and queries should use the value type (`Position`) rather than
the pointer type (`*Position`). To mutate a stored value, update it through
`Entity.Update`:

```go
if err := entity.Update[Position](world, func(p *Position) {
	p.X = 20
}); err != nil {
	return err
}
```

Components are copied into ECS storage. If a component implemented
`core.Validatable` only with a pointer receiver, change the validator to a
value receiver so the stored value still implements the interface:

```go
func (p Position) Validate() error {
	return nil
}
```

Keep shared services in world resources and refer to them from components by
value or stable ID rather than storing a service pointer as the component.

## WithDefaultSystems enables scenes

`castrum.WithDefaultSystems()` now also enables scene startup and frame
systems. To retain the 0.2.0 default set without scenes, select the systems
explicitly:

Pass `castrum.WithAnimation()`, `castrum.WithCollision()`, and
`castrum.WithTimer()` to `castrum.New` instead of `castrum.WithDefaultSystems()`.

See the [scene guide](../guides/scenes.md) for the scene lifecycle and
[`WithScenes`](../guides/scenes.md#enable-scenes) for opting in independently.
