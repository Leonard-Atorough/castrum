# v0.2.0: Control and presentation

## Intent

Give games direct control over simulation time and strengthen the camera and
audio features that are already part of the engine's core 2D workflow. After
this release, a game can pause and retime its own simulation, frame its world
with a rotated and bounded camera, and place its sounds in stereo space,
without leaving the engine's default paths.

## New features

### Game-level time control

- [ ] Add game-level pause/resume and time scaling without changing the
  fixed-timestep scheduler's deterministic contract. Pause stops fixed
  updates only; frame updates, input polling, and rendering continue so
  pause menus and overlays keep working.
- [ ] Time scaling is a single multiplier applied to the accumulator's
  elapsed-time contribution (e.g. 0.5 for slow motion, 2 for fast forward).
  Zero and negative scale values are rejected, not silently accepted.
- [ ] Make the API explicit about when changes take effect (next Advance
  call) and keep wall-clock/platform behavior separate where it should
  continue during a paused simulation.
- [ ] Define and test how pause and scale affect each subsystem: timers and
  animation advance with the fixed tick and therefore pause and scale
  automatically; audio is not auto-paused by the engine - games opt in
  through the Mixer - and interpolation alpha behavior while paused is
  documented and stable.
- [ ] Provide tests for pause, resume, scale changes mid-frame, and
  interaction with slow-frame clamping and the ticks-per-frame spiral guard.

### Camera rotation and bounds

- [ ] Add camera rotation to the primary camera's resolved view, with
  rotation-aware WorldToScreen and ScreenToWorld conversions and documented
  coordinate conventions.
- [ ] Add optional camera bounds: a world rectangle the interpolated camera
  position is clamped to, with defined behavior when the viewport exceeds
  the bounds at high zoom-out. Clamping happens after interpolation and
  before projection.
- [ ] Keep camera behavior consistent with the current transform and
  rendering model (interpolated position, rotation, zoom); defer parent-child
  transform propagation.

## Expanded features

### Audio

- [ ] Add basic pan control to the default audio path, per source, surviving
  source reconciliation (fold/restart) the way volume and pause state
  already do.
- [ ] Document and test the relationship between source state, mixer buses,
  pause, completion, pan, and OneShot cleanup, including value clamping.

### Input contract

- [ ] Verify and document mouse-wheel action semantics: whether wheel values
  are per-frame impulses or held state, and how frame-phase versus fixed-tick
  reads observe them. Add tests that pin the contract.

### Diagnostics

- [ ] Extend the opt-in debug overlay to show the current pause state and
  time scale alongside FPS/TPS, so time-control mistakes are visible during
  development. Only data the loop already collects accurately.

## Fixes and improvements

- [ ] Verify transform interpolation for translation, rotation, and scale
  across wraparound and angle boundaries (negative angles, values beyond
  2π, non-uniform scale), and document the pixel-snap behavior produced by
  view rounding.
- [ ] Update camera documentation: camera bounds become an engine feature,
  replacing the current guidance that game systems keep the camera in
  bounds.
- [ ] Sweep existing examples and guides for the new contracts and add a
  focused runnable example for pausing and scaling time and one for camera
  rotation or bounds.

## Release gates

- [ ] Tests demonstrate that the new controls do not cause duplicate or
  skipped fixed updates beyond the documented scheduler behavior.
- [ ] Update guides, API docs, and performance measurements affected by the
  changes; extend benchmarks only where new code sits on a hot path.
- [ ] Every new public feature has Go documentation, a guide or guide
  section, and a focused runnable example where appropriate.

## Explicitly not in this target

Entity hierarchy, full UI, scene management, physics response or a solver,
asynchronous/batch loading, camera shake and follow smoothing (game-system
concerns built on top of the camera), and multiple cameras/viewports remain
out of scope. They need separate lifecycle, ownership, or performance designs
rather than being bundled with time controls.
