# v0.2.0: Control and presentation

## Intent

Give games direct control over simulation time and strengthen the camera and
audio features that are already part of the engine's core 2D workflow. After
this release, a game can pause and retime its own simulation, frame its world
with a rotated and bounded camera, and place its sounds in stereo space,
without leaving the engine's default paths.

## New features

### Game-level time control

- [x] Add game-level pause/resume and time scaling without changing the
  fixed-timestep scheduler's deterministic contract. Pause stops fixed
  updates only; frame updates, input polling, and rendering continue so
  pause menus and overlays keep working.
- [x] Time scaling is a single multiplier applied to the accumulator's
  elapsed-time contribution (e.g. 0.5 for slow motion, 2 for fast forward).
  Zero and negative scale values are rejected, not silently accepted.
- [x] Make the API explicit about when changes take effect (next Advance
  call) and keep wall-clock/platform behavior separate where it should
  continue during a paused simulation.
- [x] Define and test how pause and scale affect each subsystem: timers and
  animation advance with the fixed tick and therefore pause and scale
  automatically; audio is not auto-paused by the engine - games opt in
  through the Mixer - and interpolation alpha behavior while paused is
  documented and stable.
- [x] Provide tests for pause, resume, scale changes mid-frame, and
  interaction with slow-frame clamping and the ticks-per-frame spiral guard.

### Timer groups

- [x] Add named timer groups that pause, resume, and scale their timers as
  a set, without affecting timers outside the group (#74). A timer joins a
  group through its component; an empty group name is ungrouped.
- [x] Keep the existing completion contract untouched: tick-stamped
  completions with [timer.Timer.JustCompleted] observing them, and a paused
  group holding elapsed time exactly rather than discarding it.
- [x] Group state is an engine-managed resource systems mutate: pause,
  resume, and scale calls from game code, applied by the timer system
  during advancement. Group pause is orthogonal to a timer's own Running
  state and to game-level pause.
- [x] Reject non-positive group scales, mirroring game-level time scale;
  pause is the tool for stopping.
- [x] Tests pin group pause mid-interval, resume continuity, scaling with
  repeating-timer carryover, ungrouped timers, and unknown groups reading
  as unpaused at scale 1.

### Camera rotation and bounds

- [x] Add camera rotation to the primary camera's resolved view, with
  rotation-aware WorldToScreen and ScreenToWorld conversions and documented
  coordinate conventions.
- [x] Add optional camera bounds: a world rectangle the interpolated camera
  position is clamped to, with defined behavior when the viewport exceeds
  the bounds at high zoom-out. Clamping happens after interpolation and
  before projection.
- [x] Keep camera behavior consistent with the current transform and
  rendering model (interpolated position, rotation, zoom); defer parent-child
  transform propagation.

### Easing and interpolation curves

- [x] Ship standard named easing curves - linear, quad, and cubic in-out
  and their relatives - as pure functions in geom (#76).
- [x] Add a tick-based tween helper consistent with the fixed timestep and
  the state-not-events philosophy: presentation tweens advance on frame
  time, simulation-affecting motion stays on the fixed tick.
- [x] Table-test the curves' endpoints, monotonicity, and symmetry.
- [x] Tie the curve and tween work to the transform-interpolation verification
  item under Fixes and improvements; the broader transform checks remain open.
- [x] Keep the surface minimal: no tween manager, no target bindings - the
  curves compose with existing systems; richer tooling waits for evidence.

## Expanded features

### Audio

- [x] Add basic balance control to the default audio path, per source, surviving
  source reconciliation (fold/restart) the way volume and pause state
  already do.
- [x] Document and test the relationship between source state, mixer buses,
  pause, completion, balance, and OneShot cleanup, including value clamping.

### Input contract

- [x] Verify and document frame-scoped mouse input: logical-screen cursor
  coordinates and signed wheel displacement accumulated by the backend over
  its sampling interval, with stable, non-consuming snapshot reads. Test
  snapshot fidelity and refresh, and demonstrate frame-phase wheel zoom;
  tick-scoped mouse delivery and event history remain out of scope (#17).

### Diagnostics

- [x] Extend the opt-in debug overlay to show the current pause state and
  time scale alongside FPS/TPS, so time-control mistakes are visible during
  development. Only data the loop already collects accurately.

## Fixes and improvements

- [x] Verify transform interpolation for translation, rotation, and scale
  across wraparound and angle boundaries (negative angles, values beyond
  2π, non-uniform scale), and document the pixel-snap behavior produced by
  view rounding.
- [x] Update camera documentation: camera bounds become an engine feature,
  replacing the current guidance that game systems keep the camera in
  bounds.
- [x] Sweep existing examples and guides for the new contracts and add a
  focused runnable example for pausing and scaling time and one for camera
  rotation or bounds.

## Release gates

- [x] Tests demonstrate that the new controls do not cause duplicate or
  skipped fixed updates beyond the documented scheduler behavior.
- [x] Update guides, API docs, and performance measurements affected by the
  changes; extend benchmarks only where new code sits on a hot path.
- [x] Every new public feature has Go documentation, a guide or guide
  section, and a focused runnable example where appropriate.

## Explicitly not in this target

Entity hierarchy, full UI, scene management, physics response or a solver,
asynchronous/batch loading, camera shake and follow smoothing (game-system
concerns built on top of the camera), and multiple cameras/viewports remain
out of scope. They need separate lifecycle, ownership, or performance designs
rather than being bundled with time controls.
