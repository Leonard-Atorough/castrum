# v0.3.0: Compose complete games

## Intent

Move from a set of engine subsystems toward a coherent workflow for authoring,
organizing, testing, and shipping a small 2D game. This is a proposed feature
set; narrow it using experience from v0.1 and v0.2 before implementation.

## Proposed feature set

### Game flow and derived signals

- [ ] Add a small scene/state lifecycle for switching between game states and
  cleaning up state-owned entities and resources predictably.
- [ ] Add a typed signal/event mechanism only after animation and timer
  completion semantics are established. Prefer derived transition events
  over making every component mutation publish arbitrary events.
- [ ] Document event lifetime, ordering, and whether events are delivered
  once per frame or fixed tick.

### Developer workflow and shipping

- [ ] Add a small project starter or documented project template that
  demonstrates the recommended package layout and engine setup.
- [ ] Make build and packaging guidance practical for the platforms Castrum
  officially tests; avoid implying support beyond the runner and Ebitengine
  compatibility actually verified.
- [ ] Improve development diagnostics based on v0.1 usage: the initial
  overlay may grow into queryable timing or resource diagnostics only where
  the data can be collected accurately and cheaply.

## Decision gates before implementation

- Confirm scene ownership boundaries for entities, resources, systems, and
  runner state.
- Validate the starter project and packaging workflow on the supported
  platform matrix.

## Explicitly not promised

This proposal does not commit Castrum to a visual editor, arbitrary
serialization of user components, an in-house full physics engine, or
networking, particles, or asset hot reload. Those are separate product
decisions. Tilemaps need an authoring/import format decision before runtime
support is adopted.
